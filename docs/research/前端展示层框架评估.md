# 前端展示层框架评估

初评日期：2026-10-24。复核日期：2026-10-25。关联需求：FW-R12、FW-R15、FW-R17。前提：用户已确认客户端采用 Wails 方案，主要技术背景为 Go + 前端。

本次复核推荐采用 React + TypeScript + Vite，沿用工程已有的 React 实施基线。源码当时已使用 Wails v3.0.0-beta.34、React、Radix 与统一 CSS 变量；前端组合仍属于实施选择，Wails v3 最新版由用户后续明确指定。本次迁移与真实窗口证据见 [Wails v3 验收](../implementation/2026-10-25-Wails-v3迁移与剪切相位验收.md)，框架推荐不等于全部媒体与双端门槛完成。

本轮选型结论可直接作为后续前端工作的默认依据：

| 状态 | 组合 | 适用边界 |
| --- | --- | --- |
| 用户已确定 | Wails + Go | 桌面壳与本地应用层 |
| 推荐并沿用现有实施 | React + TypeScript + Vite | 工作区、素材、字幕、属性与 AI 任务面板 |
| 推荐并沿用现有实施 | Radix + 自有共享组件 + CSS 设计变量 | 基础交互和统一视觉；可参考 shadcn/ui 的组件组织 |
| 独立设计与验证 | 时间线高频绘制、音频时钟、视频预览 | 使用稳定接口连接普通 UI，按真实负载验证 |
| 按需增加 | Zustand、TanStack Virtual、Tailwind、React Compiler | 出现明确需求或分析结果后采用，不因选定 React 一次性加入 |

React 是本项目当前的工程推荐，不是 AI 编码成功率或运行速度排名。若后续确认团队在 Vue 上有明显经验优势，或实际原型证明当前更新机制存在难以隔离的瓶颈，再评估切换成本；不为比较框架同时维护多套完整工作台。

## 1. 推荐方案

**推荐 React + TypeScript + Vite；普通 UI 使用 Radix 基础交互组件与项目共享组件，统一 CSS 设计变量。shadcn/ui 可作为组件设计与代码参考；时间线、播放头、波形和媒体预览按负载分层。**

核心组合与可选工具分开：React/TypeScript/Vite 构成展示层基线；Tailwind CSS、Zustand、TanStack Virtual 仅在组件需求、兼容性或实测负载需要时加入。工程当前未使用这些可选依赖。后续采用 shadcn/ui 的原始组件时需一并评估其样式与底层组件依赖，不能将“参考其设计”写成已经接入完整 shadcn 工具链。

针对本轮“AI 友好、性能合理、现代化”三个条件，建议落到以下选择：

| 条件 | 本项目的选择 | 需要承担的代价 |
| --- | --- | --- |
| AI 辅助开发与长期维护 | React + 严格 TypeScript，集中维护共享组件、桥接类型和设计规范 | 约束 hooks、异步状态与订阅范围；不能让 AI 任意复制页面和引入依赖 |
| 剪辑时交互性能 | 面板用 React，可见片段按视区显示，播放头与波形独立更新，媒体计算交给原生层 | 需要设计绘制与数据边界，单换框架不能解决全部卡顿 |
| 现代化且符合剪辑习惯 | Radix 交互原语 + 自有设计变量，参考 shadcn/ui 的可组合组件 | 自行维护桌面密度、键盘和焦点行为；组件库不会自动产出合适的剪辑工作台 |

这里的“AI 友好”包含开发工具能读懂和可靠修改界面；产品内的模型调用、任务恢复和 Agent 工具由 Go 应用层组织，均不依赖 React 专有接口。未来如有必要替换展示层，可以复用工程核心、任务和媒体协议，不将模型供应商直接耦合到 UI 组件。

Radix 提供不预设视觉样式的基础组件，处理焦点、键盘和部分可访问行为，适合作为自有工作台的基础；仍需项目对最终组合做验收。[Radix 官方介绍](https://www.radix-ui.com/primitives/docs/overview/introduction)

2026-10-25 核查 Wails v3 官方 FAQ：React、Vue 和 Svelte 均有模板与 TypeScript 变体，服务绑定可生成 TypeScript 定义，因此 Go 背景并不将前端限定为其中某一个框架。当前桌面工作台可由 Vite 构建静态资源并连接 Go 服务，无需另设 Node 服务或服务端渲染。[Wails v3 官方 FAQ](https://v3.wails.io/faq/)、[Vite 生产构建](https://vite.dev/guide/build)

选择 React 主要基于复杂编辑器的组件组合、类型约束、代码可读性和维护路径。当前没有本项目的 LLM 编码成功率、运行性能或开发耗时对照实验，因此不宣称“AI 写 React 一定优于其他框架”或“React 最快”。

截至本轮查阅，React 官方列出的最新版本为 19.3。实施时核对 Wails 模板与组件兼容并锁定具体版本，不沿用模板中的旧版本，也不把文档中的当前版本当作永久固定值。[React 版本](https://react.dev/versions)

## 2. 如何理解 AI 友好

这里主要指便于 Codex/Claude Code 等工具协助开发和维护界面，不是要求展示层自己承担模型推理。

评估标准包括：

- 官方文档和当前版本规范可检索，可获得可靠示例，避免混用旧 API。
- TypeScript 能约束组件、命令和桥接数据，错误可以通过类型检查及时发现。
- 共享组件与明确目录使 AI 能找到已有实现，而非为每个页面重复生成一套。
- UI 状态、工程状态和高频绘制职责分开，局部修改不会牵动整个编辑器。
- 组件源码和设计规则可见，便于检查键盘、焦点、样式和状态行为。
- 有格式、类型、组件与实际 WebView 验证，不能只凭截图或生成的代码看起来合理。

shadcn/ui 官方将开放可修改的组件代码、可组合接口及便于 AI 理解作为设计特点，并提供读取项目配置的官方 Skill。这些是可供后续采用的辅助条件，不代表本项目已安装该 Skill。代码纳入工程后，其升级、质量和可访问性仍由项目维护。[shadcn/ui 说明](https://ui.shadcn.com/docs)、[shadcn 官方 Skills](https://ui.shadcn.com/docs/skills)

Svelte 也提供官方 AI 工具、文档 MCP、Skills 和静态分析支持，不能简单将它归为“不适合 AI”。本项目推荐 React 是工程组合判断，不是对训练数据规模或模型能力的未经验证排名。[Svelte AI 工具](https://svelte.dev/docs/ai/overview)

## 3. React、Vue 与 Svelte 的取舍

下表为定性评估，不是本项目实测成绩。

| 维度 | React + TypeScript | Vue + TypeScript | Svelte + TypeScript |
| --- | --- | --- | --- |
| 组件组织 | TSX、组合与 hooks，适合统一代码约束 | 单文件组件、模板与 Composition API，表达清楚 | 编译型组件与响应式机制，表达紧凑 |
| AI 协作 | 小组件、严格类型和源码可读 UI 组合有利 | 同样可用严格类型与统一组件；已有 Vue 经验时很有吸引力 | 官方 AI 工具可提供当前文档和纠错，需要固定当前写法 |
| 更新性能 | 需约束订阅范围，避免无关树更新 | 需关注大对象的响应追踪和列表更新 | 编译与响应式可减少部分运行时工作，但不能消除 DOM/绘制成本 |
| 复杂编辑界面 | 推荐结合可组合组件与专用绘制模块 | 可实现相同编辑器，若团队熟悉 Vue，迁移成本可更低 | 可实现；需逐项确认目标组件、面板、虚拟化及维护路径 |
| 现代视觉 | 由设计系统与组件决定 | 由设计系统与组件决定 | 由设计系统与组件决定 |
| 本项目结论 | 当前首选建议 | 团队已有明显 Vue 优势时的合理替代 | 轻量路线候选，不作为当前首选 |

本项目的排序依据是复杂编辑工作区的组件组合、可检查的类型与源码、后续维护和现有基线复用。若团队后续确认长期主要使用 Vue，可以重新比较迁移成本；当前没有理由仅为追逐框架热度更换已建立的 React 基线。也不依据简单计数器基准宣称某一框架能带来更快的视频解码或导出。

React Compiler 可以在构建期自动做部分记忆化优化，主要改善重复渲染和计算；它不替代虚拟化、资源预算、媒体引擎和绘制架构。Vue 官方也强调大型列表要虚拟化，深层大数据需要相应的响应性策略；Svelte 官方说明其组件由编译器转换为优化的 JavaScript。[React Compiler](https://react.dev/learn/react-compiler/introduction)、[Vue 性能](https://vuejs.org/guide/best-practices/performance)、[Svelte 编译模型](https://svelte.dev/docs/svelte/overview)

不将四种状态管理、两套 UI 组件和多个渲染框架同时引入。先选一套普通 UI 主路径，再让时间线与媒体模块通过稳定接口扩展。

## 4. 建议的前端组合及边界

| 层 | 建议 | 作用及限制 |
| --- | --- | --- |
| 页面与组件 | React + TypeScript | 面板、素材库、字幕内容、生成任务与属性编辑 |
| 开发与构建 | Vite | 构建供 Wails 加载的静态资源；本轮没有需要新增 Node 服务的前提 |
| 基础 UI | Radix + 项目共享组件；shadcn/ui 作为可选参考 | 统一对话框、提示、按钮、菜单等；固定一种基础交互体系，按需补组件 |
| 样式 | CSS 设计变量 + 普通 CSS；Tailwind CSS 可选 | 共享颜色角色、字体、密度、焦点和组件状态；当前不为选框架额外更换样式工具 |
| UI 状态 | React 局部状态与外部订阅；Zustand 候选 | 选中项、面板、筛选、任务视图等；工程权威数据与撤销仍归 Go 核心 |
| 长列表 | TanStack Virtual 候选 | 素材、转写、字幕和可见轨道虚拟化；它不提供完整时间线剪辑语义 |
| 高频绘制 | requestAnimationFrame + DOM transform / Canvas 2D | 播放头、刻度、波形等，按实测负载选择；复杂 GPU 图形库后加 |
| 媒体画面 | Wails 与原生媒体服务之间经验证的预览链路 | 不将正式视频帧通过普通 React 状态或 JSON 桥逐帧搬运 |

shadcn/ui 提供 Vite 接入说明；TanStack Virtual 支持列表及横向/纵向组合虚拟化，保留样式控制。[shadcn Vite 指南](https://ui.shadcn.com/docs/installation/vite)、[TanStack Virtual](https://tanstack.com/virtual/latest/docs/introduction)、[Zustand 官方仓库](https://github.com/pmndrs/zustand)

Wails 负责桌面窗口和 Go 桥接，选择 React 并不意味着采用 Electron。Vite 的开发工具依赖与最终运行依赖分开统计；若其他模块另带 Node 适配器，需要单独记录，而非归因于 React 本身。

## 5. 编辑器性能的分层原则

### 普通交互层

React 管理操作面板、表单、选区状态和低频任务变化。组件订阅所需字段或片段，不让一个全局播放时间变化触发素材库、聊天、属性和所有片段更新。全局 context 中避免放置每帧变化的庞大对象。

外部时钟与工程读模型可以通过独立订阅连接界面；React 官方提供 `useSyncExternalStore`。使用该 API 本身仍不能避免过宽订阅导致的更新，需检查实际组件边界。[React 外部状态订阅](https://react.dev/reference/react/useSyncExternalStore)

### 时间线与高频层

- 播放头可用 requestAnimationFrame 驱动 transform，不要求整个 React 树每帧渲染。
- 拖动时保留局部预览状态，在约定节奏校验并在完成手势时通过统一命令提交；撤销粒度不能变成每个 pointermove 一条。
- 波形、时间刻度和密集标记可用 Canvas 2D，先做有界缓存与按视区绘制；不要因为“视频软件”就从第一天引入大型 GPU 图形引擎。
- 片段优先使用可见区 DOM 加时间/轨道裁剪，实测需要时再增加画布覆盖；画布保留键盘、文字输入和可访问的 DOM 操作入口。
- 素材、字幕、转写和日志仅渲染可见部分，并区分虚拟列表与后台数据分页。
- 生成进度、转写和聊天事件合并更新，避免每个 token、日志或进度事件驱动全工作区重排。

### 权威状态与媒体层

Go 工程核心拥有片段编排、版本和历史；前端维护读模型与暂态选择。采用 revision、稳定 ID、命令结果和事件同步，避免前后端各自维护互不一致的“最终时间线”。错误、过期结果和重复命令沿既有契约处理。

React Compiler 或手工记忆化可以在分析后启用，不能作为不用做负载测试的理由。本轮没有播放帧率或虚拟化片段规模的实测数据。

## 6. 现代化界面的具体方向

界面目标是一张安静、可精确操作的剪辑工作台。预览和时间线是视觉中心，生成与 AI 工具围绕当前素材和选区提供帮助。当前设计变量与组件基线见 [DESIGN.md](../../DESIGN.md)，具体色板、字号和尺寸仍需通过真实素材与双端界面验证。

建议工作区：顶部工程与导出操作；左侧素材/转写；中间预览；右侧属性和可收起的 AI/生成面板；下方可调高的时间线。小窗口可折叠侧栏、切换面板；不通过整体等比缩小让所有控件变得难用。

现代感来自：

- 明确的中性色表面层级，预览周围保持安静，强调色用于选中、焦点和关键行动。
- 适度紧凑的桌面密度，控件、图标、间距和弹出层一致，避免大块装饰卡片挤压工作区。
- 等宽时间码和稳定数字宽度；素材名、字幕、长中文和错误内容都有完整查看路径。
- 清楚的拖放反馈、吸附、选区范围、撤销和忙碌状态，减少隐藏在 hover 中的关键功能。
- 保持操作位置稳定，生成与下载不会突然改变面板尺寸或移动导出按钮。
- 界面动效用于表达状态和因果，尊重减少动态设置；避免播放时有无关持续动画。
- 深浅主题可预留语义映射，首个视觉方案按真实素材和使用环境评估，不能只在漂亮演示素材上成立。

可形成产品识别的细节是“选区上下文条”：让时间线选区、预览和 AI 面板呈现一致的对象、范围及可执行操作，帮助用户知道这次生成或编辑会影响哪里。它表达真实编辑关系，不使用装饰性胶片边框。

## 7. Wails WebView 兼容门槛

Wails 支持的系统范围与现代 CSS/组件支持范围必须分别核查。例如 Tailwind v4 官方列出 Chrome 111、Safari 16.4、Firefox 128 等基线；Vite 当前默认构建目标也有自己的浏览器范围，降低 JavaScript 构建目标并不自动补齐 CSS 和所有平台 API。[Tailwind 兼容性](https://tailwindcss.com/docs/compatibility)、[Vite 构建目标](https://vite.dev/guide/build)

因此，先确认 Windows/macOS 最低系统与实际 WebView，再锁定组件、样式和构建配置。当前 CSS 变量路线也需做兼容检查；不引入 Tailwind 并不自动证明全部 CSS 可用。若最低系统不能满足方案，要选择可维护的兼容实现，不能只改 `build.target` 后宣称全部兼容。

实际验收包含：菜单/弹出层、输入法、文件拖放、键盘、Canvas 清晰度、缩放、滚动、焦点、高 DPI、原生预览遮挡、窗口调整和睡眠唤醒。Chrome 浏览器中的效果不等于 macOS WKWebView 中已经通过。

## 8. AI 辅助开发的项目约束

- TypeScript 严格模式，Wails 生成绑定只经一个桥接适配模块使用；UI 不直接散落版本相关调用。
- 普通 UI、编辑命令、时间线绘制和媒体预览分别组织，公共组件集中复用。
- 统一原语与组件状态，按需加入依赖，不让 AI 为相同控件混用多套组件库。
- Go 核心维持工程与业务规则；前端优化不能绕过锁轨、源区间和撤销事务。
- 禁止把平台 API 主密钥或模型秘密放进前端、组件、Skills 或工程文件。
- 默认用工程既有中文术语和明确动作标签，输入法组合输入时不误触快捷键或发送。
- 类型检查、组件测试、前端性能剖析与实际 Wails 双端运行结果共同作为验收，不能只看 AI 输出的完成说明。

本轮不创建 Next.js/Nuxt/SvelteKit 服务端流程。它们可以服务其他产品需求，但当前本地工作台以静态前端接 Go 服务即可，不应只因为 AI 常生成全栈模板就增加运行时。

“便于 AI 开发”和“允许产品内 Agent 编辑工程”分别验收：前者检查工具能否在既有组件与严格类型约束下可靠修改界面；后者检查所有编辑入口是否仍经 Go 的统一命令、版本校验和撤销。二者不要求采用同一种模型 SDK，也不让 Agent 通过直接修改 React 状态完成正式剪辑。

前端框架也不改变源码保护边界：React、Vue、Svelte 最终交付的 JavaScript/CSS 都应视为可检查资源。模型凭据、授权判断与需保护的核心规则沿 Go、系统凭据和适合联网的服务端边界组织，不能把更换框架作为防反编译方案。保护及商业发行要求继续见 [桌面客户端技术栈评估](桌面客户端技术栈评估.md)。

## 9. 实施与验收顺序

1. 先用 Wails + 推荐前端建立最小工作区，确认实际版本、WebView、设计变量和组件原语。
2. 验证可调面板、普通菜单/对话框、中文输入和键盘焦点，形成共享组件与状态样例。
3. 使用代表性素材、字幕、轨道与片段数据，测量渲染、拖动、缩放和长列表；让普通面板与高频区域保持隔离。
4. 接入原生预览及 Go 命令，测量事件和 IPC 对交互的影响，校验撤销与状态冲突。
5. 在 Windows/macOS 实际 WebView 上复验，记录 CPU、内存、交互和定位分位数，并检查 CSS 与原生视图行为。

性能验证使用同一套工程夹具，先记录既有实现，再按瓶颈优化；不为选型额外搭建三套完整编辑器：

| 夹具层次 | 建议内容 | 重点观测 |
| --- | --- | --- |
| 日常工作区 | 约 100 个片段，素材、字幕和属性面板同时打开 | 拖动/修剪/缩放响应、普通面板是否被播放头带动更新 |
| 密集工程 | 约 1,000 个片段与 10,000 条字幕或转写行，仅挂载可见部分 | DOM 数、渲染耗时、内存峰值、输入延迟 p50/p95 |
| 压力工程 | 逐步增加至 10,000 个片段，持续播放/定位并更新后台任务 | 性能拐点、缓存上界、任务对 UI 的干扰与长时内存走势 |

这些数字是建议的测试输入，不是当前已支持的产品容量；交互阈值及最低设备另行确定。媒体解码、合成与导出另测，固定素材、预览质量和硬件，避免将媒体开销误记为框架差异。只有出现与 React 更新模型相关且难以隔离的实际瓶颈，才有依据讨论更换框架。

框架选型不能代替上述验收。当前工作区与局部验证见 [首轮实现与验收](../implementation/2026-10-25-首轮实现与验收.md)；双端真实 WebView、复杂时间线负载及完整媒体预览仍需验证。本次复核保留 React 展示层推荐，不将已有窄样本结果扩展为完整性能承诺。
