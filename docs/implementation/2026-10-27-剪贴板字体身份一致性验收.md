# 剪贴板字体身份一致性验收

2026-10-27，FW-R01/FW-R03/FW-R11/FW-R12，P1/P2。修复工程字体与复制快照组合中的资源身份遗漏，保留常规文字/字幕、统一编辑和MCP边界。原完整目标继续，Windows实机与模型账户按用户指令后置。

## 问题和修复

原剪贴板只登记Clip.AssetID和LUT.AssetID，没有把TextStyle.FontAssetID加入资源身份集合。因此，复制后即使同ID字体已换成不同内容，粘贴仍会提交，并通过相同fontAssetId使用新字体。文字、单独复制字幕和随源复制的绑定字幕都能复现。

先添加行为回归，修复前上述三项均实际返回nil，没有触发应有的clipboard_asset拒绝。应用层另用真实Go Regular/Go Mono TTF构造同一工程的另一份有效文件，保持projectId/sequenceId/fontAssetId并更换实际字体内容；通过OpenProjectPath打开后，使用最新sourceEpoch和revision，旧剪贴板也静默接受了新字体。该测试同样在修复前失败，证据保存在本阶段before-fix日志。

应用普通编辑接口本来禁止直接add/update_asset，此限制保持。核心测试用公开引擎命令核对数据契约，应用测试用真实读取/打开接口，不为复现开放绕过路径，也不宣称普通GUI存在任意素材身份改写入口。

修复只在[快照采集](../../internal/editor/clipboard.go)补齐字体引用，让字体复用原资源深拷贝、身份比较、64MiB预算和原子粘贴逻辑。快照不复制字体字节，不增工程字段或新权限。不同指纹/元信息或缺失先拒绝；路径、名称和临时URL仍排除于内容身份，同内容重定位继续可用。默认系统字体的空引用保持原行为，不能据此保证不同系统默认字形一致。

## 核心与应用检查

- 三种复制形式均拒绝同ID字体内容变化，失败不改变工程/修订、剪贴板或撤销历史。
- 同内容路径、显示名和临时URL变化仍能粘贴，字体引用及字幕人工样式保持；一次Undo/Redo恢复整组副本和身份。
- 原字体缺失时，在创建任何片段之前报clipboard_asset，空工程及历史保持。
- 应用重开同ID工程后，最新作用域请求仍校验字体内容，旧剪贴板保留，新引擎不多出失败操作的历史。

editor、application、projectstore、projectfonts、localagent、workflows共6个相关包竞态回归通过，相关核心/应用/字体静态检查通过。新增5个顶层测试覆盖上述分支与真实媒体；测试中缺失字体的比较基线改为NewEngine规范化后的Snapshot，避免将nil/空列表初始化差别误判为粘贴修改。

## 真实原生字体

使用既有随包MLT/Qt和Go Regular TTF，在320×180/30fps工程中创建实际文字。先检查基线不是纯色空白，再读取30帧RGBA。复制后实际移动原字体文件至中文/空格路径，用RelinkAsset核验同内容，然后删除原片段并从旧快照粘贴至第60帧。

粘贴后的30帧、一次Undo/Redo以及保存重开后的30帧，均与原基线逐字节一致：每份6912000字节，SHA256为1f6ee529073c91c6f769d50bf79539775ada30acd43e8e65e6a8dbc2e965995a。另实际重跑Go Regular/Go Mono原生对照，确认两份不同TTF生成不同字形，避免将空白或统一默认字体回退当作一致性证明。

以上是本机两份静态TTF及当前SDK的证据，不代表所有字体、复杂文字或Windows渲染均已验收。本轮没有前端交互/视觉改动和新的GUI操作复查；原生字体证据来自真实媒体会话，前端390项及序列界面沿上阶段记录，不声称本轮重跑。
