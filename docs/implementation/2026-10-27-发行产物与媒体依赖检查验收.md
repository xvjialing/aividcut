## 已实现的可重复入口

新增internal/releaseaudit与cmd/release-audit，标准库实现，未加入第三方依赖。显式JSON配置目标OS/架构、包根、自有app/worker/ffmpeg/ffprobe、MLT模块和profile目录以及可选前端dist。相对路径基于配置文件解析，不自动发现系统SDK或读取用户凭据。示例见[发行输入配置](../../build/release-audit.example.json)，模块约束见[说明](../../internal/releaseaudit/README.md)。

```sh
make release-audit
make release-check
go run ./cmd/release-audit -config /absolute/path/config.json
```

release-audit输出可归档JSON；release-check先跑真实production嵌入资源测试，再执行严格检查。默认不执行被查程序，明确-probe-ffmpeg才对配置中的同OS/架构FFmpeg/FFprobe运行固定-version，不接受额外shell或参数。跨端PE静态检查可以在Mac执行；跨端程序运行、Windows安装及GUI仍需Windows环境。

报告记录普通文件字节/SHA256、thin/fat Mach-O或PE架构/普通导入表、Go实际版本/模块/部分构建选项、调试段、运行时目录内容摘要及链接。包外文件、外链库、外链SDK目录和symlink分开报告。前端扫描源码扩展名、map及跨读取块的内联映射；未把整文件装入内存。

单文件512MiB、每目录8192文件/32768节点/2GiB、配置64KiB，32产物/8运行时目录；版本进程3秒/64KiB，前后SHA绑定证据。检查期间文件/目录变化或超界不算通过，目录内symlink不递归跟随，相关摘要不冒充目标文件内容。实际分析另对明确选择的7个模块目标读取指纹，和工具默认扫描能力分别归档。

生成报告成功退出0；-check遇blocker/review退出1；配置或无法完成的检查退出2。releaseVerified始终false，许可闭包留人工核对，静态清单不能作为最终法律授权或发行验收。未知DLL不会自动归为系统库，延迟导入、动态LoadLibrary、Qt/MLT插件和传递依赖仍有覆盖限制；Go模块清单也不是完整SBOM。

| 输入 | 当前证据 | 实际含义 |
| --- | --- | --- |
| macOS主程序 | arm64 Mach-O，18081776字节，13条普通系统导入，无DWARF，trimpath=true，嵌入Wails v3.0.0/Go1.27.3 | 自有壳已有实际编译产物；不证明前端/协议不可研究 |

| MLT开发目录 | 7个symlink到包外Cellar，profiles同样在包外 | 新电脑不能靠这些开发机路径取得运行时 |

Mac完整随包候选输入得到58条blocker与10条review；Windows输入得到5条blocker与1条review。计数按产物/链接逐项记录，属于当前配置的发现数量，不是全系统缺陷总量。Mac主要为3个外置工具、46个包外直接链接记录、2个包外运行时目录及7个外链模块；Windows的媒体worker、FFmpeg、FFprobe和两类MLT运行时没有提供。默认报告正常生成，严格检查两个目标均退出1，未以“报告成功”替代发行通过。

主客户端文件沿上一轮最终构建，本轮没有改剪辑代码或重建主客户端。分别独立读取所有app/worker/ffmpeg/ffprobe文件SHA256，与报告完全相同。macOS本地codesign严格校验通过，详情为Signature=adhoc、TeamIdentifier未设置，仍没有Developer ID、公证或Windows商业签名证据。检查工具自身完成Mac arm64/Windows amd64编译，不作为主客户端Windows运行证据。

实际输入报告：[Mac](evidence/release-audit/macos-report.json)、[Windows](evidence/release-audit/windows-report.json)。源文件路径是开发机证据，不是建议让最终安装包继续依赖这些绝对路径。

## 许可和保护边界

FFmpeg官方说明默认许可与可选GPL部分有关，并提供与具体二进制对应的源码/构建及动态链接核对要求；本机配置已明确启用GPL，不能只看顶层项目名称就把当前SDK标为LGPL发行。[FFmpeg官方许可说明](https://www.ffmpeg.org/legal.html)。此处是分发评审问题，不将GPL等同于禁止商业使用。

本机MLT Homebrew配方开启GPL/GPL3，而选定normalize模块对应上游7.42.0的volume源文件标注GPL；顶层COPYING不足以概括所有加载模块。[对应版本volume源码](https://raw.githubusercontent.com/mltframework/mlt/v7.42.0/src/modules/normalize/filter_volume.c)。同版本qtext源文件为LGPL 2.1或以后，单个文件的许可同样不能代替整个Qt/MLT构建闭包。[对应版本qtext源码](https://raw.githubusercontent.com/mltframework/mlt/v7.42.0/src/modules/qt/filter_qtext.cpp)。尚未把全部源码与本机二进制逐项绑定，保持待审。

Qt官方说明符合LGPLv3要求时可保留应用闭源，同时存在GPL专属模块及商业许可选择。需要按实际Qt组件、链接与用户权利安排复核。[Qt官方LGPL义务](https://www.qt.io/development/open-source-lgpl-obligations)。本工程的Qt位于媒体文字/字体路径，客户端仍是已确定的Wails；进程隔离、去符号和Wails本身的许可都不能替代媒体依赖的分发判断。

后续可审方案包括：为闭源核心验证所需的LGPL媒体构建及合适编码器；或审查GPL媒体worker的源码/分发安排和Go核心边界；Qt等具体组件也可评估相应商业许可。具体路线尚未定型，不能通过给某个组件购买许可就推断整个FFmpeg组合已改成专有许可。现有libx264、LUT、文字和音频效果本轮保持，不为了检查变绿暗换编码器或删插件。

去符号/trimpath仅提高还原成本；前端资源、Skills、协议和界面行为仍能被读取研究。运行时目录清单不代表CPU/GPU/显存指标完成，安装体积也不替代编辑负载性能。自有业务核心、第三方库、用户凭据和发布签名仍沿已归档的分层保护要求。

## 生产资源和失败路径

新增production测试遍历真正嵌入的embed.FS，拒绝.ts/.tsx/.jsx/.map与内联source map，保留原有HTML资源可用性测试。实际在生成目录以独占方式临时放入一个合成source map，production测试按预期失败并指出该文件；finally只移除本次身份匹配的夹具后，完整production测试恢复通过。没有将失败屏蔽或仅测试独立dist副本，也未改用户素材。

Go标准库当前pe.ImportedLibraries仍为空实现，本轮没有将其nil当作“Windows无依赖”，而是有界读取普通导入描述符。真实Windows交叉编译产物能读取kernel32.dll，另用OriginalFirstThunk=0的合法描述符、异常RVA与未知DLL验证解析和分类。fat头支持属于静态实现，当前真实产物样本为thin，未扩张成universal发行验证。

版本输出洪泛测试发现嵌入bytes.Buffer会暴露ReaderFrom绕过Write限额，已改为私有buffer字段，受控进程越界会被取消。相关测试还验证固定参数、具体角色、SHA不匹配、未知配置/尾随数据/超大文件、前端跨块映射及外链目录；没有执行用户模型或未知网络脚本。
